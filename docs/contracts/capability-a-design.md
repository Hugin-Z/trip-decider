## 1. 问题实证

不是判断，是 2026-08-03 拿真实数据跑出来的两条死路
（`scripts/smoke_action_loop.py`）。

### 1.1 候选完全不响应意图

**输入**：`origin=武汉`、`destination_expression=想找个山里安静的地方待两天`、
`themes=["自然风光"]`、行程窗 2 天、`total_budget_cny=4000`。

**输出**（两次独立运行）：

| 运行 | 候选 |
|---|---|
| 1 | 上海市 |
| 2 | 乌鲁木齐市、兰州市、北京市 |

从武汉出发、两天的行程窗，候选给出乌鲁木齐——单程直线距离约 2500 公里。
既不响应「山里安静」，也不考虑往返可达性。

**根因定位**：`dynamic_discovery.py:114-120` 的排序键只有 **POI 命中数与标签
字典序**，没有任何目标函数。`guided_discovery.py:502-513` 的
`playable_time_seconds` 在同一 intent 下只反映往返车程差。基线报告 M5 与
`PLAN.md` §10 补注早已把「差异化」记为**一句未实现的承诺**；本轮把它从判断
变成了实证。

### 1.2 候选连车次都查不到，动作循环因此震荡

选定候选后推进动作循环：

```
railway 域：missing / exact_station_identity_not_found
map 域    ：estimated
web 域    ：sourced
```

`get_next_actions` 在 `ACTIONS_AVAILABLE` 与 `NEED_USER_INPUT` 之间**反复震荡
八轮不收敛**，PlanVersion 从未安装，A12（修改重排）经此路径走不到。

**根因**：候选生成器提出了铁路采集器解析不出车站身份的目的地。两条死路
**同源**——候选阶段没有任何证据纪律，它推荐的地方没人验证过「到得了」。

### 1.3 这为什么是产品定义问题，不是排序 bug

`PLAN.md` §1 的产品定义是 **Plan-backed**：候选不是搜索结果，是**背后至少跑通
一个粗粒度可行方案**的方案。v3 时代就冻结了这条，一直没实现。

一个查不到车次的城市成为候选，违反的不是「排得不好」，是**产品定义本身**。
所以能力 A 的核心不是排序算法，是**候选阶段的证据纪律**。

## 2. 设计目标

### 2.1 Plan-backed 的可操作定义

> 一个目的地能成为候选，当且仅当：系统已经为它跑通了一个**粗粒度可行方案**，
> 且该方案的每一条关键事实都有证据支撑。

「粗粒度可行方案」的最小内容 **【待批：下表是提案】**：

| 项 | 要求 | 证据来源 |
|---|---|---|
| 去程 | 至少一个可达车次，有发车/到达时刻 | 12306 实采 |
| 返程 | 同上，且落在行程窗内 | 12306 实采 |
| 可玩时长 | 行程窗减去往返车程与缓冲后的净余时间 > 阈值 | 由上两项推导 |
| 目的地身份 | 能解析出行政区（name/adcode） | 高德实采 |

**底线**：**车次查不到的目的地不得成为候选**（§1.2 的直接教训）。这不是
排序权重低，是**不进候选集**。

### 2.2 「山里安静」这类意图如何结构化

现状：`intent.themes` 是一个字符串列表（`travel_agent.py` 的 `TravelIntent`），
`destination_expression` 是自由文本。`themes=["自然风光"]` 这种粒度**不足以**
表达「山里」（地形）+「安静」（人流强度）。

**【待批：三个选项】**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 保持 `themes` 自由词表，检索时做同义扩展 | 改动最小；但「安静」无法进入过滤，只能进排序，且没有可解释判据 |
| B | 新增结构化字段：`terrain`（山/水/城/野）、`crowding`（安静/适中/不忌）、`intensity`（体力强度） | 意图可机械过滤；需要意图解析把自由文本映射到枚举，映射本身要有证据纪律（映射错了是「猜」） |
| C | B 的字段 + 保留 `themes` 作为补充信号 | 表达力最好；字段最多，`TravelIntent` 与落盘契约都要动 |

**倾向 B/C**——理由：`crowding` 这类维度若只进排序，就会退化成「神秘匹配分」，
而 `PLAN.md` §10 明文**不输出神秘匹配分**。能过滤才能解释。

**但有一个硬约束需要先答 【待批】**：`terrain` / `crowding` 的取值**从哪来**？
高德 POI 有类别标签，但没有「安静」这种属性。若靠模型给一个目的地打
「安静」标签，那正是产品定义禁止的「用模型猜测替代证据」。
可选出路：(i) 只做能证据化的维度（地形可从 POI 类别推），把「安静」降级为
用户自述偏好、不参与过滤只做提示；(ii) 找到可引用的来源；(iii) 明确接受这一维
为 `estimated` support 并要求 conditional。

### 2.3 可达圈：用现有 12306 采集器做粗筛

`PLAN.md` §10 写了「高铁 2h/4h 圈」，从没实现。

**提案**：可达圈不预计算，**按需实采**。给定 origin 与行程窗，对候选池里的每个
目的地跑一次 12306 查询，拿到往返车次后按下式过滤：

```
净可玩时长 = 行程窗长度 - 去程车程 - 返程车程 - 首末段缓冲
候选保留条件：净可玩时长 >= 每天 min_playable_hours × 天数   【待批：阈值】
```

**代价与【待批】**：候选池若有 N 个目的地，就是 N 次 12306 查询。实测单次
约数秒，N=20 就是分钟级。三个选项：

| 选项 | 做法 |
|---|---|
| 1 | 先用地理距离粗筛到 N≤5，再实采验证 |
| 2 | 全量实采，接受耗时，加进度反馈 |
| 3 | 缓存可达圈结果（origin × 目的地 × 日期粒度），走 `evidence_broker` 既有缓存 |

**倾向 1+3**：距离粗筛不需要证据（它是几何事实，不是对现实的断言），
实采只对少数候选做，结果进缓存。注意距离粗筛**只能用于缩小池子，不能用于
排序**——排序必须基于实采到的车程。

### 2.4 排序目标函数

**硬约束：不输出神秘匹配分**（`PLAN.md` §10）。因此排序必须是**可解释的
分项**，每项都能对用户说清「为什么它排前面」。

**提案：三个分项，各自可解释，不合成单一分数** **【待批】**

| 分项 | 判据 | 呈现 |
|---|---|---|
| 可达性 | 净可玩时长（小时），实采车程推导 | 「两天里有 26 小时可玩」 |
| 主题匹配 | 命中的结构化维度**逐条列出**，不打分 | 「地形：山 ✓；主题：自然风光 ✓」 |
| 差异化 | 与其他候选的**取舍差异**，成对描述 | 「比 X 远 1 小时，但人少」 |

**关键设计选择**：**不合成总分**。候选卡并列展示三个分项，排序用可达性
（唯一有客观标度的那个），主题与差异化只做呈现。理由：合成权重就是神秘
匹配分，而权重无法向用户解释，也无法证伪。

**【待批：替代方案】** 若必须有确定顺序，可用字典序：可达性分档（充裕/勉强）
→ 主题命中数 → 名称。仍然可解释。

## 3. 证据纪律

### 3.0 红线管整条供应链，包括开发时写进数据文件的数

**2026-08-03 记录。** 实现 v0 时最省事的做法是把 28 个坐标直接写进 catalog——
凭记忆写，大概率还都对。**没写。** 那是没有来源的地理断言，与运行时让模型给
目的地打「安静」标签是同一种违规，只是换了入口：一个在运行时进，一个在开发时
就烘进数据文件，后者更难查，因为文件看起来像事实。

这是产品红线第一次约束到**执行者自己对世界的知识**，而不只是约束运行时的模型
输出。凡是要落进仓库的、关于世界的具体数值，都要有来源；「我知道」不是来源。

### 3.1 每个候选必须携带的最小证据集

| 域 | 最低要求 | 达不到时 |
|---|---|---|
| railway | 去返程各一个车次，`support == sourced` | **不进候选集**（§1.2 教训） |
| map | 目的地行政区身份可解析 | **不进候选集**——身份不明的地方谈不上「去」 |
| web | 景点候选非空 | 可进候选集，标 `unknown` + `next_action` |

**railway 与 map 是准入门槛，web 是可降级项。** 判据：前两者决定「到不到得了、
是不是一个确定的地方」，后者决定「到了做什么」——后者缺失是信息不足，
前两者缺失是候选本身不成立。

### 3.2 与既有契约的衔接

候选卡的 `evidence_statuses` 与 `next_action` **沿用现契约不新增机制**：

- 每域一条 `{domain, token, next_action?}`，token 由 `project_domain` 按读取
  时刻算（I5/I6 不破）；
- `token != verified` 必须带 `next_action`（I3a 双向约束）；
- 候选阶段的证据落 `evidence/guided-comparison.json`（容器 C，独立性已有裁决）。

**新增的是准入过滤，不是新的证据形状。** 这一点很重要：§3.1 的门槛用现有
token 表达（`railway` 域 token 的 support 必须是 `sourced`），不引入第二套判据。

## 4. 分期

### 4.1 v0 最小可用

**验收判据**：输入「从武汉出发、想找个山里安静的地方待两天」，输出 2–3 个
**可达且相关**的候选，每个都能继续走到 PlanVersion。

范围：
- §2.3 的可达圈粗筛（距离粗筛 + 实采验证）
- §3.1 的准入门槛（railway/map 必须 sourced）
- §2.4 的三分项呈现，排序用可达性
- 意图结构化取**最小集**：只做能证据化的维度 **【待批：见 §2.2 的硬约束】**

**明确不做**：「安静」这类无证据来源的维度进入过滤；成对差异化描述；
候选池的智能扩展（v0 用一个固定的种子来源，见下）。

**v0 的候选池从哪来 【待批】**：现在 `dynamic_discovery` 用高德 POI 检索。
`examples/destination_catalog.json`（P5 轮 1 移出 `src/` 的那份）有 28 个国内
目的地，可作为 v0 的种子池——但它是**城市专属数据**，直接读回 `src/` 会违反
I9。若用它，必须作为**用户可替换的配置**从 `src/` 外注入，不是内置。

### 4.2 v1 完整

`PLAN.md` §10 全量：可达圈的两档（2h/4h）、差异化目标函数、
「必须保留 / 删除 / 换天 / 降低强度」的交互升级（后者依赖修改日志的高频动作
统计，`PLAN.md` §10 已写明判据）。

**切分线**：v0 证明「Plan-backed 候选能产出」，v1 证明「候选之间有真正的
差异化取舍」。前者是能不能用，后者是好不好用。

## 6. 七条裁决（已定稿）

**裁决出处：Hugin 经网页端 Claude 评审确认，2026-08-03。**

出处必须写：这七条的裁决发生在仓库**之外**的对话里。上一轮的报告末尾还写着
「7 条待批项还没批」，作业单直接说「已全批」——从仓库能查到的记录看，
「待批」到「已批」之间没有出处。仓库外发生的决定，落仓库时必须注明何人、
何时、何处，否则下一个人无从判断它是裁决还是某一轮的即兴。

| # | 事项 | 裁决 |
|---|---|---|
| 1 | 粗粒度可行方案的最小内容 | 往返车次（实查）+ 净可玩时长 ≥ 阈值 + ≥1 个匹配主题的锚点 POI |
| 2 | 意图结构化 | 选 **C**：结构化字段接可查证维度，自由词表保留原话供提示层 |
| 3 | 无证据来源的维度 | **模型标签只做过滤和提示，不进排序输入。**「可能符合『安静』（推测）+ 建议确认」可以；「按安静程度排序」不行——`estimated` 不进可比较的量 |
| 4 | 可达圈实采策略 | 按需实采 + 池子预筛（砍到 ≤10 再逐个查车次）；预筛判据只缩池不排序。**执行见下方修正** |
| 5 | 净可玩时长阈值 | 总时长 **50%**，标可调，真实数据来了复核 |
| 6 | 排序 | **不合成总分**，三分项并列，只按可达性排 |
| 7 | v0 种子池 | `examples/destination_catalog.json`，运行时经数据目录加载（不进 `src/`，I9 不破）；中期换高德城市级检索 |

### 6.1 裁决 4 的执行修正（2026-08-03，实测后）

原文是「粗**距离**砍到 ≤10」。实测种子池**没有坐标**——28 条记录 16 个字段，
没有任何一个是地理坐标。设计 §2.3 那句「距离粗筛不需要证据（它是几何事实）」
的前提是坐标现成，不成立。

取坐标的实测代价：单条约 12 秒（婺源 14.9s、三清山 15.4s、大理 5.0s），
28 条约 **330 秒**，且 3 个样本里 **1 个解析不到**（大理 UNMATCHED）。
**预筛比它要省的东西还贵**，而且会静默缩小池子。

**执行改为**：预筛用 catalog **自述属性**——主题命中 + `suggested_days` 与行程窗
匹配——砍到 ≤10，再逐个实查车次。距离判据留待坐标补齐后替换（中期解，
坐标来源由 Hugin 定：高德批量取 + 人工抽核，或权威地理数据；管线不动只换判据）。

这是**判据替换不是目的偏离**：裁决 4 的目的（池子砍到 ≤10 再实查）与第二半
（预筛判据不进排序）都保留，可达性判定一条不少地交给 12306 实查。

**否决 C（保留距离预筛、坐标走 `poi_coordinate` 缓存）的理由**：5.5 分钟首跑
只是 28 条的代价，而 catalog 中期要换成高德城市级检索、池子会变大，取坐标的
成本线性涨——**C 是给一个会变大的池子选了个不 scale 的判据**。
