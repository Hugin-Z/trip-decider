# 第三方时刻表 vs 12306 实查：宿主那份行程的对账

**素材来源**：第四次宿主实测中，宿主回退 web search 后自己排出的行程（第四/五
张图）。它的车次与票价来自第三方时刻表站与检索结果，**全程没有出处断言**。

**核验时间**：2026-08-04 20:08–20:09（+08:00）
**核验方式**：`verify_railway_assertions`，逐条实查 12306
**耗时**：1 条 8.0 秒（几乎全是会话初始化），4 条 14.3 秒

## 对账表

|---|---|---|---|---|
| 1 | G1521 武汉→上饶 | 08:05 → 11:46，¥340 | 该日该线路查无此车次 | `unknown` |

## 逐条说明

### 第 2 条是**确凿的错**

G1992 确实存在、确实在那天跑那条线，但第三方给的：

- **发车时刻早了 33 分钟**（断言 15:35，实际 15:02）。按断言去车站，车已经开走
  半小时。
- **票价高了 ¥137.5**（断言 ¥340，实际二等座 ¥202.5）。两个人就是 ¥275 的预算
  误差。

这一条是本次核验最有价值的产出：它不是「查不到」，是**查到了而且对不上**。

### 三条 `unknown` **不等于「这些车次不存在」**

必须说清楚，否则这份对账就是在冤枉第三方。`unknown` 的准确含义是「按你给的
车次号 + 线路 + 日期这个组合，12306 上查不到」。可能的原因至少有：日期超出预售
期、站名写法不同、车次当日停运、或者查询本身失败。

**已排除的一个解释：站名写法。** 用 汉口 / 武昌 分别重查 G1521 与 G868，仍然
`unknown`——所以不是「武汉」这个写法太笼统导致的。

**一个反向佐证：** G4392 在 **08-11** 查得到（18:26 → 18:50），只是不在断言说的
08-12 09:12。也就是说这趟车真实存在于该线路，第三方给错的是**日期或时刻**。

所以更可能的情况是：第三方给的车次-线路-时刻组合本身就不准，而不是我们查不动。
但**工具不做这个推断**——它只报「查无实据」并建议出发前确认，把判断留给用户。
这正是三档而非两档的意义。

---

## 这份对账说明了什么

宿主第四次实测的完整叙事是：

1. 它先想用 trip-decider；
2. `verify_itinerary` 4 分钟无响应；
3. 它回退 web search，自己排了一份看起来很完整的行程；
4. **那份行程里 4 条车次断言，1 条确凿有错、3 条查无实据、0 条站得住。**

第 3 步产出的东西，用户没有任何办法分辨对错——这正是这个项目要解决的问题。
而第 2 步（工具不可用）直接导致了第 4 步（用户拿到一份不可信的行程）。所以
「响应时间」不是性能优化，是**能不能兑现核心价值**的前提。

## 复现

```
PYTHONPATH=src python - <<'PY'
from trip_decider.itinerary_verification import verify_railway_assertions
print(verify_railway_assertions([
  {"train_code":"G1992","origin_station":"上饶","destination_station":"武汉",
   "departure_at":"2026-08-14T15:35","arrival_at":"2026-08-14T19:12","price_cny":340.0},
])["summary"]["sentence"])
PY
```

断言集已入夹具：`tests/test_verify_itinerary_batching.py` 的
`HOST_ITINERARY_ASSERTIONS`（**真实车次号未脱敏**——它是对账素材，改了就失去
意义）。

**注意**：车次时刻与票价会随日期变化，重跑本文件的命令得到的结果**不会**与上表
逐字相同。上表是 2026-08-04 那一刻的实查快照，价值在于「当时对不上」这个事实，
不在于数字本身可复现。
