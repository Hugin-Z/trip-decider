# 第六次复测要点（预期是最后一次）

第五次是**最接近成功的一次**：全链路走到详细规划的最后一步，12306 实查带余票
在场，local_transit 展开兑现，宿主全程按证据规矩行事（卡住时先实查再提交）。
终点死在 map 域看门狗，宿主给出的归因精确到可以直接照着查代码。

本轮修的就是那一处，外加它背后的病理。

---

## 本轮修了什么

| # | 第五次的症状 | 归因 | 现在 |
|---|---|---|---|
| 1 | 看门狗写着 30 秒、~5 秒就触发 | **比较对象错**：等待用的是 `min(30, remaining)`，而 `remaining` 是「本次调用还能花多久」（MCP 传的 5 秒），不是「动作多久算卡住」。报文里的 30 是另写的字面量 | 拆成两个数：`ACTION_STALL_SECONDS=30`（唯一出处，判定与报文同源）与调用预算 |
| 2 | 高德 26 秒正常完成却被判超时 | 同上 | 预算用完只回「还在飞」，不怪动作、不动 run 状态 |
| 3 | 主循环反复重发、永远等不到 | **重发不去重**：旧的还在飞，新的又发出去 | `_IN_FLIGHT` 登记，同一动作已在飞就拒发 |
| 4 | 迟到的结果没人收 | 超时把 run 打成 BLOCKED、动作状态翻成 blocked，两道门把迟到结果挡掉丢弃 | 两道门都放行仍在飞的那一次——超时是「这次没等到」，不是「结果作废」 |
| 5 | （未发生但同族）无限转圈 | — | 连续超时到 3 次熔断为 `{DOMAIN}_ACTION_FAILED` |

**顺带发现并修掉一个镜像缺陷**：后台线程的驱动预算原本裸写 `30.0`，与看门狗
阈值**恰好相等**，于是真卡住的动作会和预算耗尽赛跑——预算先到就被判成「还在
飞」，run 永远 RUNNING、看门狗一次也响不了。现在从阈值派生
（`ACTION_STALL_SECONDS + 15`）并有用例守住大小关系。

1. **重启 Claude Desktop**；2. **开新对话**；3. 打开 MCP 日志便于取证。

## 场景 A：map 域慢查询不再误判（本轮核心）

沿用第五次那句输入，走到详细规划。重点看 map 域那一步。

| # | 看什么 | 通过 |
|---|---|---|
| A1 | 有没有 `tool.timeout` 事件 | 高德在 30 秒内返回时**不该有**。第五次是 26 秒被误判 |
| A2 | 若确实出现 timeout | 事件 `details.timeout_seconds` 必须是 **30**，且与实际等待时长相符（不再是「写 30 等 5」） |
| A3 | 同一个动作被派发几次 | **1 次**。日志里同一 `tool.started` + 同域不该连着出现多条 |
| A4 | 慢查询最终返回后 | 结果应入库；下一轮不再重查该域 |
| A5 | 整体 | 能走完详细规划，不再卡在 map |

## 场景 B：熔断（大概率不会触发，触发了要看对）

只有连续 3 次超时才熔断。若真撞上：

| # | 看什么 | 通过 |
|---|---|---|
| B1 | error_code | `MAP_ACTION_FAILED`（不是 STALLED） |
| B2 | 事件里 | `consecutive_timeouts` 与 `max_consecutive_timeouts` 都在场 |
| B3 | next_call | 给得出重查 / 手工提交两条出路 |

## 场景 C：住宿价格仍是 unknown（预期之内，不是缺陷）

问「住哪、多少钱」。

**通过标准**：给出住宿**片区**与候选酒店名字位置，价格明说不知道。

本轮实查确认高德 POI **一个价格字段都没有**（`cost`/`price`/`avg_price`/`均价`
全为 0 次；唯一沾边的 `rating` 是评分不是价格）。所以这不是精度问题而是字段
不存在，I4 维持登记，评估已入 ledger。**看到这里是 unknown 请不要记为缺陷。**
